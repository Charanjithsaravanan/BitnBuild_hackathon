# Experiment API

A FastAPI backend for a browser-based behavioral-experiment SaaS platform.

## Included

- Researcher authentication with JWT access tokens
- Experiment CRUD
- Versioned experiment definitions
- Draft -> published lifecycle
- Public participant session creation
- Trial response ingestion with reaction-time metadata
- Session completion
- JSON and CSV result export
- CORS configuration
- SQLite for local development and PostgreSQL-compatible SQLAlchemy URLs
- Basic request validation, ownership checks, and rate-limit-ready boundaries
- API documentation at `/docs`

## Architecture

```text
Researcher UI
     |
     v
 FastAPI API -------------------- PostgreSQL / SQLite
     |
     +---- Auth
     +---- Experiment definitions + versions
     +---- Public participant sessions
     +---- Trial responses
     +---- Analytics/export
```

## API flow

1. `POST /api/v1/auth/register`
2. `POST /api/v1/auth/login`
3. `POST /api/v1/experiments`
4. `PUT /api/v1/experiments/{id}/draft`
5. `POST /api/v1/experiments/{id}/publish`
6. Participant uses `GET /api/v1/public/experiments/{slug}`
7. Participant starts with `POST /api/v1/public/experiments/{slug}/sessions`
8. Browser records each trial with `POST /api/v1/public/sessions/{session_id}/responses` or buffers trials with `POST /api/v1/public/sessions/{session_id}/responses/batch`
9. Participant finishes with `POST /api/v1/public/sessions/{session_id}/complete`
10. Researcher exports with `GET /api/v1/experiments/{id}/results.csv`

## Definition format

The published definition supports a sequence of trial blocks. Example:

```json
{
  "settings": {
    "fullscreen": true,
    "randomize_trials": false,
    "collect_device_info": true
  },
  "blocks": [
    {
      "id": "intro",
      "type": "instruction",
      "text": "Press F for blue and J for green.",
      "duration_ms": null
    },
    {
      "id": "trial-1",
      "type": "stimulus",
      "stimulus": {"kind": "text", "value": "BLUE"},
      "duration_ms": 1000,
      "expected_response": "f"
    }
  ]
}
```

## Timing design

The API deliberately stores both participant/browser timing and server receipt timing:

- `client_started_at`: ISO timestamp generated by browser
- `client_event_time_ms`: browser event-clock value if supplied
- `client_duration_ms`: browser-measured response duration
- `server_received_at`: server receipt timestamp
- `client_event_id`: client-generated idempotency key for deduplication

The platform should use browser high-resolution timing (`performance.now()`) for reaction-time measurement. Server timestamps are for auditing, ordering, and transport-delay analysis; they should not be presented as the participant's true reaction time.
